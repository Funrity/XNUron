# XNUron → эмулятор iOS: анализ осуществимости и статус

Документ написан по результатам исследования и реализации первого этапа. Всё, что здесь названо «проверено»,
проверено тестами из `tests/run_all.sh`. Юридические замечания — не юридическая консультация.

## 1. Короткий вывод

**Загрузить настоящую iOS на XNUron сейчас невозможно, и это не вопрос «дописать ещё инструкций».**
Интерпретатор ARM64 — необходимая, но малая часть. Причины конкретные:

| # | Препятствие | Где именно упирается |
|---|-------------|----------------------|
| 1 | **Цепочка загрузки и подписи.** SecureROM → LLB/iBoot → XNU. Каждый компонент — контейнер IMG4 с манифестом (IM4M), который Apple подписывает персонально (ECID устройства, одноразовый nonce). | В a64virt нет boot ROM, который бы это проверял или использовал. Обход проверок = патчинг загрузчиков Apple, это вне проекта. |
| 2 | **Шифрование компонентов.** Часть образов (например, прошивка SEP, а в старых версиях ядро/загрузчики) зашифрована AES; ключи обёрнуты аппаратным ключом GID. | Ключей нет ни в образе, ни в проекте. Инспектор честно показывает «KBAG present». |
| 3 | **SoC Apple.** XNU ожидает конкретное железо: контроллер прерываний AIC, UART S5L, PMGR, AMCC, сопроцессоры (SEP, дисплей/DCP, ANS-накопитель), AGX GPU, DeviceTree с адресами всего этого. | Нужна модель каждого устройства «как у Apple». Публичной документации нет — только реверс-инжиниринг. |
| 4 | **Возможности ЦП.** Ядро использует MMU с 16 КБ страницами, PAC, SIMD/FP, атомики LSE, закрытые регистры Apple (SPRR/GXF и др.). | В ядре XNUron: **нет MMU, нет FP/SIMD, нет LSE, нет PAC, нет регистров Apple.** |
| 5 | **Графика.** SpringBoard/UIKit/CoreAnimation рисуют через Metal и GPU Apple. | Без модели AGX нет экрана блокировки и домашнего экрана. |
| 6 | **Userland.** Даже с работающим ядром нужны dyld, shared cache, libSystem и тысячи вызовов BSD/Mach. | Реализованы только `exit`, `write`, `getpid` в user-режиме. |
| 7 | **Скорость.** Чистый интерпретатор на хосте-разработчике: ~110 млн инстр./с (Xeon 2.8 ГГц, измерено; **на телефоне не измерялось**). | Загрузка современного XNU — это порядок миллиардов инструкций; без JIT/threaded-кода это крайне медленно. |
| 7a | **Старые устройства — 32-битные.** iPhone/iPod до A7 (S5L8900…S5L8955) — ARMv6/ARMv7, AArch32. Ядро XNUron исполняет только AArch64. | Инспектор распознаёт 32-битные Mach-O, контейнеры 8900/IMG2/IMG3 и IPSW по имени SoC и прямо так и пишет. |
| 8 | **Android.** Приложениям недоступен KVM; а гостю всё равно нужен Apple SoC, а не просто ARM64. | Аппаратная виртуализация проблему не решает. |
| 9 | **Лицензия.** IPSW можно скачать у Apple, но лицензия iOS ограничивает использование оборудованием Apple; получение ключей/обход подписи затрагивает DMCA §1201 в ряде юрисдикций. Правовой статус эмуляции спорный (известны судебные споры вокруг коммерческого эмулятора Corellium). | XNUron **не скачивает, не содержит и не изменяет** прошивки Apple и не обращается с ключами. |

Из публичных проектов сообщества известны QEMU-модели отдельных SoC Apple, доходившие до запуска ядра/части userland
**на пропатченных компонентах** и для конкретных версий; насколько мне известно, без эмуляции GPU до рабочего UI они
не доходили. Проверяйте актуальное состояние самостоятельно. Это масштаб работы, на порядки превышающий данный этап.

## 2. Годится ли существующее ядро как основа?

Да как **основа**, нет как «почти готово». Исходное ядро v0.1 (~230 строк): только целочисленный EL0, плоская память,
HLE-сисколы, ошибка → остановка. В этом этапе оно расширено (см. §3), старый API (`a64_init`, `a64_run`, поля `A64`)
сохранён, все старые тесты проходят.

## 3. Что реализовано и проверено

**Ядро (`arm64.c`, `arm64.h`)** — два режима:
- `A64_MODE_USER` (как раньше): EL0, HLE-сисколы Linux (`x8`, `svc #0`) и XNU/BSD (`x16`, `svc #0x80`, ошибки по соглашению Darwin: флаг C + errno).
- `A64_MODE_SYSTEM`: EL0/EL1, векторы исключений (VBAR_EL1), ESR/ELR/SPSR/FAR, `ERET`, раздельные SP_EL0/SP_EL1, DAIF, IRQ,
  виртуальный таймер ЦП (CNTV_*, 24 МГц, `WFI` ускоряет виртуальное время), MMIO-шина, системные регистры (MRS/MSR),
  ловушки привилегированных регистров с EL0 (EC=0x18), исключения при неверной выборке/доступе/неопределённой инструкции.
- Набор инструкций: данные (imm/reg/ext, ADC/SBC, CCMP, CSEL-семейство, бит-поля, EXTR, RBIT/REV/CLZ/CLS, UDIV/SDIV, сдвиги, MADD…UMULH),
  память (все размеры/знаковые, pre/post-index, регистровое смещение, литералы, LDP/STP/LDPSW, LDXR/STXR/LDAR/STLR),
  ветвления (B/BL/B.cond/CBZ/TBZ/BR/BLR/RET/ERET), барьеры/хинты/SYS как NOP, PAC-хинты как NOP.
- Диагностика: история последних PC, «double fault» при пустом VBAR, явный отказ при включении MMU (а не молчаливое игнорирование).

**Машина `a64virt` (`machine.c`)**: RAM 0x40000000, UART (PL011-подмножество), дисплей 270×480 XRGB8888, сенсор с IRQ, syscon (poweroff),
журнал загрузки, остановка из другого потока. Не имеет отношения к SoC Apple.

**Тестовое гостевое ядро (`guest/`, собственный код, не iOS)**: загружается на a64virt и проходит свои проверки (арифметика, атомики,
SVC на EL1, data abort с FAR/ESR, UDF, таймер-IRQ через WFI, EL0 с SVC и ловушкой MRS), затем рисует на экране и реагирует на касания.

**Загрузчики/инспектор (`macho.c`, `img4.c`, `zipinfo.c`, `inspect.c`)**:
- Mach-O arm64 (в т.ч. fat): сегменты, точка входа, dylib'ы, подпись, шифрование; запускается в user-режиме **только** самодостаточный
  исполняемый файл (проверено настоящим Mach-O из `ld64.lld`, использующим BSD-сисколы). Файлы с dylib/dyld, FileSet-ядра, FairPlay отклоняются с причиной.
- IMG4/IM4P (DER): тип компонента, KBAG, IM4M, формат полезной нагрузки.
- ZIP/IPSW (включая zip64, произвольный доступ — подходит для многогигабайтных IPSW): состав и вердикт.

**Android-интерфейс**: выбор источника (встроенное тестовое ядро, v0.1-демо, файл как Mach-O, файл как raw-образ), старт/стоп,
экран гостя (реальный фреймбуфер, касания), журнал загрузки, вкладка диагностики. Никаких нарисованных «iOS-оболочек».

## 4. Как проверялось

`tests/run_all.sh` (6 групп): старые тесты; 13 830 тестов отдельных инструкций (ожидания считает независимая Python-модель
`tools/gen_asm_tests.py`); дифференциальный тест (один C-код на x86 и в эмуляторе при -O0…-O3, итоговые хэши совпадают);
системный режим с гостем; загрузчики; JNI из обычной JVM. Намеренные поломки ядра (мутации) тестами обнаруживаются.

**Не проверено:** сборка APK и работа на реальном Android — в среде не было Android SDK/NDK. Java-код проверен только компиляцией
по моим заглушкам API (возможны расхождения с реальным SDK); CMake-сборка в NDK не запускалась (сборка на хосте тем же набором файлов — да).

## 5. Ограничения (явно)

Нет: MMU, EL2/EL3, AArch32, FP/SIMD, LSE-атомиков, PAC (PAC-хинты — NOP, подпись не вычисляется), кэшей/TLB (операции — NOP),
нескольких ядер, regs Apple, dyld/libSystem/Mach-IPC, декомпрессии LZFSE/LZSS, дешифрования чего-либо, выполнения iOS-приложений.

## 6. Следующие технические шаги (по порядку пользы)

1. MMU (стадия 1, гранулы 4/16 КБ, TTBR0/1, TCR, ASID, права, исключения трансляции) — без него нельзя запустить ни XNU, ни современный Linux.
2. FP/SIMD (NEON) — используется всем userland iOS; затем LSE-атомики и модель PAC.
3. Для проверки CPU+MMU на легальной цели: загрузка небольшого ядра Linux arm64 (данные собственной сборки) на a64virt с DeviceTree.
4. Производительность: threaded-код/JIT для ARM64 хоста, кэш декодирования.
5. Только после п.1–2 имеет смысл исследовать Apple-специфику: DeviceTree/boot-args XNU, AIC, UART, регистры SPRR/GXF; LZFSE для распаковки собственных легально полученных компонентов.
6. User-режим: загрузчик dyld-образов и HLE libSystem (по аналогии с проектами уровня совместимости ОС), Mach-ловушки/IPC.
7. GPU/графика — отдельный, самый непрозрачный этап.

## 7. Структура

```
app/src/main/cpp/   arm64.[ch] ядро · machine.[ch] a64virt · macho.[ch] · inspect.[ch] img4.c zipinfo.c · native-lib.cpp (JNI) · guest_image.h (сгенерирован)
app/src/main/java/  MainActivity, EmuView, Native
guest/              тестовое гостевое ядро (start.S, kernel.c, link.ld);  tools/build_guest.sh пересобирает guest_image.h
tests/ tools/       тесты и генератор тестов инструкций
```


## Додаток (0.2.2): режим «попытка запуска IPSW»

Реализовано: извлечение kernelcache из IPSW, снятие IM4P/IMG4, распаковка LZFSE и complzss, загрузка arm64-ядра в память, boot_args/DeviceTree, запуск на EL1.
Не реализовано и не будет обходиться: расшифровка (KBAG/GID), проверка и подмена подписей. Ожидаемый результат на реальном ядре — остановка эмулятора в первых инструкциях
(системные регистры Apple, PAC/SIMD, включение MMU). Это реальный результат, а не загрузка iOS.
